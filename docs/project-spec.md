# Genetics Results API - Project Specification

## Purpose

A FastAPI-based REST API that serves human genetics association results and annotations. It provides read-only access to tabix-indexed data files stored on Google Cloud Storage, enabling queries by genomic region, variant, gene, and phenotype across multiple genetic studies and datasets.

## Architecture

### Tech Stack
- **Python 3.13** with **FastAPI** and **uvicorn**
- **htslib/tabix** for indexed genomic data access (compiled in Docker image)
- **Google Cloud Storage** for data files (accessed via gcloud-aio-storage, gcsfs)
- **Polars** for data manipulation
- **Bearer token / reverse-proxy header** authentication (user API tokens validated by the chat backend — the recommended programmatic credential; shared internal secret; Google Identity Tokens verified with `google-auth` — deprecated, still supported). No application code imports `jwt` directly, but `PyJWT` is pinned in `pyproject.toml` on purpose and must NOT be dropped: it is a hard transitive requirement of `gcloud-aio-auth` (`pyjwt>=1.5.3,<3.0.0`), pulled in by the direct `gcloud-aio-storage` dependency, and `google.oauth2.id_token.verify_token` — the function behind the Identity Token path in `app/core/auth.py` — imports it lazily via `PyJWKClient` whenever the certs endpoint returns JWK rather than x.509 format. The explicit pin keeps the version exact instead of letting the transitive range float.
- **uv** for dependency management
- Deployed as a Docker container (base: nikolaik/python-nodejs)

### API Endpoints (all under `/api/v1`)

| Tag | Domain |
|-----|--------|
| authentication | Auth status only: `GET /auth` (public, hidden from the schema) reports whether the request carries an oauth2-proxy/IAP identity. No login or token issuance — tokens are minted elsewhere |
| metadata | Dataset and resource metadata |
| search | Search across phenotypes, genes, variants (includes gene coordinates via GENCODE) |
| credible-sets | Fine-mapping credible set results. The variant-row endpoints (`credible_sets_by_phenotype`, `_by_id`, `_by_region`, `_by_variant` GET/POST, `_by_gene`, `_by_qtl_gene`) accept an optional `coding_only=true` query param that restricts returned rows to coding variants by their inline `most_severe` consequence, reusing `config.common.coding_set`; rows with a missing/NA `most_severe` are excluded. Default (`false`) is unchanged. Applied via header-aware `filter_stream_by_coding` (TSV) / `filter_coding_rows` (JSON) in `app/core/streams.py`, wired through `range_response` for the range endpoints. `_by_gene`, `_by_variant` (GET) and `_by_qtl_gene` additionally accept `data_types=<comma-separated>` (GWAS, eQTL, pQTL, sQTL, caQTL, metaboQTL), which restricts rows by their inline `data_type` column, matched case-insensitively; it runs on the same `range_response` path via the generic `filter_stream_by_column` / `filter_rows_by_column` that `coding_only` is now built on. An unrecognized type yields an empty result rather than unfiltered rows. These three endpoints are the ones the mcp-server tools expose a QTL-type filter for — the filter previously existed only client-side and was silently dropped by the API (see "Undeclared query parameters" below). Two endpoints take neither filter: `credible_sets_by_phenotype_leads` reduces a phenotype's file to one lead variant per `cs_id` while streaming it (the row flagged by an `is_lead`/`lead` column if present, else highest `pip` with ties broken by `mlog10p`; `format` defaults to `json` here, not `tsv`), and `credible_sets/{id_or_resource}/stats` returns per-trait credible-set counts (risk/protective, each with coding and LoF breakdowns) for a data file or a whole resource. |
| colocalization | Colocalization analysis results |
| expression | Gene expression data (eQTL, etc.) |
| genes | Gene information, lookups, and nearest genes with coordinates |
| gene-groups | HGNC gene-group membership (`GET /gene_group/members?group_id=\|group_name=[&exclude_olfactory=]` returns all descendant member genes by lineage, with symbol/ensembl/coords; `exclude_olfactory=true` drops olfactory receptors) and symbol normalization (`GET /gene/normalize?symbols=<comma-separated>` resolves approved/alias/previous symbols to current approved HGNC symbols) |
| gene-disease | Gene-disease associations |
| gene-based | Gene burden test results. `gene_based/{gene}` (hidden from the schema) merges one gene's rows across every configured dataset from their combined gene-locus-indexed files, where the genebass file carries only its `mlog10p_burden > 4` hits; passing `traits=<comma-separated trait_original>` switches it to the unfiltered per-trait files, so a gene with no significant result in a named trait still comes back (capped at 50 traits per request, since each costs a tabix subprocess per dataset that has it). `gene_based_results_by_phenotype/{resource}/{phenotype_or_study}` streams one trait's complete unfiltered results (every gene x annotation class, `format=tsv\|json`) from those same per-trait files — the same objects BigQuery's `gene_burden_results` is loaded from. Several data files of one resource can share a per-trait directory (the three IBD entries do), so both paths dedup by resolved file path rather than by data file id. **The burden files are point-indexed on `gene_start_pos` (`-s5 -b6 -e6`, begin and end both column 6), so a gene query only hits when the file's coordinates come from exactly the dataset's configured `gencode_version`** — the same silent-empty-result trap as the QTL gene files above. The IBD entries were configured `43` while `munge_ibd_exome.py` annotates with v45, which hid 111 of its 19,108 genes (APC, ATM, BMPR1A, BIRC3 among them) from `/gene_based/{gene}` entirely; v45 is now in `gencode_versions` and the IBD entries declare it |
| chromatin-peaks | Chromatin accessibility peaks. `peak_to_genes/{peak_id}` (genes linked to a peak) and `gene_to_peaks/{gene}` (its inverse: peaks linked to a gene, per cell type); both include gene coordinates and return the identical column set |
| open-chromatin | Open-chromatin peak atlas (accessible/active regulatory regions labeled by cell type/tissue/condition). `open_chromatin/region/{chrom}/{start}/{end}`, `open_chromatin/variant/{variant}` and `open_chromatin/peak/{peak_id}` are interval-OVERLAP queries (a peak matches when its `[start, end]` overlaps the query), unlike the point-indexed products below; all three take `resources` and `format=tsv\|json` |
| variant-effect | In-silico predicted variant effect on chromatin accessibility (ChromBPNet + FLARE): `variant_effect/variant/{variant}`, `variant_effect/region/{chrom}/{start}/{end}`, `variant_effect/gene/{gene}` (one-sided `window`, default 0 = the gene itself). Files are point-indexed on the variant position; config granularity is one entry per DATASET, so the `marderstein` resource ships two predictor files (`marderstein_chrombpnet`, `marderstein_flare`) |
| mpra | MPRA-measured allelic regulatory activity (emVar/active/log2Skew calls): `mpra/variant/{variant}`, `mpra/region/{chrom}/{start}/{end}`, `mpra/gene/{gene}` (same `window` semantics). One LONG point-indexed file per dataset, one row per variant x cell line |
| hla | Classical HLA allele associations. `GET /hla/{resource}?phenotypes=<comma-separated>[&genes=<comma-separated>]` returns every imputed HLA allele tested against those phenotypes (187 alleles across 10 genes), and `GET /hla/genes` returns the locus registry. The association unit is an **allele**, not a variant: the files carry `gene`/`allele` instead of `ref`/`alt`, so there is deliberately no by-variant form and `/summary_stats` can never match a row. Storage is per-phenotype tabix files registered in the profile `summary_stats` config under `data_type: hla`, so the read path is `SumstatsDataAccess`; only the merge ordering differs (`SORT_CONFIG_HLA` on chr/pos/allele, selected per data_type, because the files have no ref/alt to sort on). Every allele of a gene sits at that gene's single anchor position, so `genes` is served by `stream_sumstats_positions` — discrete point reads at the selected anchors rather than the span between them, which would otherwise drag in every gene lying in between. HLA-DRB3/4/5 share one placeholder anchor and cannot be separated positionally. Cross-phenotype queries ("which traits is `B*27:05` associated with?") span all 2,712 files and are answered from BigQuery `hla_associations_v`, not here |
| exome-results | Exome sequencing association results |
| phenotype | Phenotype descriptions |
| resources | Available resource listing |
| datasets | Dataset configuration (`GET /datasets`; `GET /dataset_display_names` returns display-name overrides keyed by the raw `dataset` column value) |
| rsid | rsID to variant mapping. `GET\|POST /rsid/variants` take a comma-separated list (query parameter and request body respectively) and answer one object per distinct id. Both are `@is_public`, and both are bounded at `MAX_RSIDS` (5 000) ids per request — 422 above it, and the POST additionally stops reading its body at `MAX_RSID_BODY_BYTES` (413). The bound applies to **every** caller with no exception for a sandbox credential: the route is relaxed by `app/core/limits.py`, so an unbounded id count meant a caller that omitted its sandbox token got a looser limit than one that presented it. 5 000 is above what the GET can carry anyway (h11 caps the request line and headers at 16 KiB, and the shortest id costs 4 bytes in the query string), so nothing that works today regresses |
| summary-stats | GWAS summary statistics. `GET\|POST /summary_stats/{resource}/{data_type}` query one or more variants across one or more phenotypes; `GET /summary_stats_by_region/{resource}/{data_type}/{region}` returns every record in a genomic range (`chr:start-end`, X accepted) for the given phenotypes. All three take `phenotypes=<comma-separated>` and `format=tsv\|json`, fan out one tabix query per (phenotype, data file), and heap-merge the results into a single union-of-columns schema prefixed with `resource`/`version`/`phenotype`. `phenotypes` is required on the range endpoint too: summary stats live in per-phenotype files, so unlike `credible_sets_by_region` there is no combined file spanning a region across traits. The range is validated by the shared `RequestUtil.validate_range`, so the same `max_range_size_stream` (10Mb TSV) / `max_range_size_json` (5Mb JSON) caps apply, and every phenotype multiplies the row count within them |
| variant-annotation | Variant annotation data (FinnGen, etc.) |
| variant-sets | Named curated variant lists from `variant_set_files` (`GET /variant_sets` lists the names, `GET /variant_sets/{name}` expands one into `chr:pos:ref:alt` ids; unparseable lines are skipped rather than served) |

### Undeclared query parameters

`reject_unknown_query_params` (`app/core/query_params.py`) is registered as an app-level dependency next to `auth_required` and returns **422** for any query parameter the matched route does not declare. FastAPI's default is to ignore undeclared parameters, which made client/API drift invisible: the mcp-server tools advertised a `data_types` filter that no endpoint implemented, so a caller asking for one association type kept receiving every type and had no way to notice — the resulting oversized response was then truncated by the LLM tool-result cap, hiding exactly the rows that had been asked for. The dependency reads the declared aliases off `request.scope["route"].dependant` (recursing into sub-dependencies) and caches them on the route object, so the check costs one set difference per request. The error lists both the offending parameters and the accepted ones, which is what lets an agent self-correct.

### JSON range responses advertise their columns (`X-Columns`)

A JSON range response is a **bare array** of row objects, so an empty one is `[]` and carries
no schema whatsoever — a consumer building a dataframe from it cannot tell "no rows matched"
from "no such column", and the genetics SDK raised `ColumnNotFoundError` on an ordinary
no-hit query (`genetics-results-suite-6uk`). `range_response`'s JSON branch therefore sets an
**`X-Columns` response header** holding the served file's own header line, comma-separated.
One change in `app/core/responses.py` covers every JSON range endpoint — all 23 call sites
across the 11 routers that use `range_response`.

**Not covered**: endpoints that compute JSON directly instead of streaming a TSV through
`range_response` — `search`, gene annotations (`genes.py`), gene groups (`gene_groups.py`),
rsID lookup (`rsid.py`), gene-disease (`gene_disease.py`), and gene-based/gene-burden results
(`gene_based.py`, `TimedJSONResponse`/`StreamingResponse` directly). These have no header line
to advertise and degrade to the pre-existing behaviour.

- **The names come from the FILE header, not from `header_schema`.**
  `tsv_stream_to_list_with_header` returns the header it already reads and keys the rows by;
  `header_schema` is a validating superset used for type coercion (see
  `genetics-results-suite-7yg`) and would over-claim on a file carrying fewer columns.
  The header line is read even when there are zero data rows, which is what makes the empty
  case work at all.
- **Additive, deliberately.** The body is byte-identical, so the browser and the MCP server —
  both of which parse the array — cannot observe the change. Wrapping the array in an
  envelope would have broken both.
- **JSON only.** On the TSV path the header line is already the first line of the body, and
  `genetics-results-suite-7yg` established that path must not buffer the stream to inspect it.
- **Row filters do not change it.** `coding_only` and `data_types` drop rows, never columns,
  including down to zero rows.
- **Fail-open.** Header values are latin-1 encoded by Starlette and the value is
  comma-delimited, so `columns_header` omits the header rather than 500ing if a column name
  ever cannot survive that round trip. Nothing today has such a name.
- **Not exposed via CORS.** It is not in the `CORSMiddleware` allow/expose lists, so browser
  JavaScript cannot read it; the consumer that needs it (mcp-server's `ToolExecutor`) is
  server-side. Add it to `expose_headers` if a browser consumer ever needs it.

Pinned by `tests/test_columns_header.py` (offline lane).

### Data Access Pattern

1. **Configuration-driven**: Each data resource is defined in `app/config/` with paths to GCS-hosted tabix files and column mappings. Dataset metadata (author, version, description, metadata_file, harmonizer type) is loaded from a shared `configs/datasets.yaml` file via `app/config/yaml_loader.py`, which selects the active profile from the `CONFIG_PROFILE` env var and reads the YAML path from `DATASETS_CONFIG_PATH` (default: `./configs/datasets.yaml`). The canonical YAML lives in the suite repo and is synced to each service repo for local dev. Product configs (credible_sets, exome_results, gene_based_results, summary_stats) reference the registry via `dataset_id` and contain only file paths and product-specific settings.
2. **Range queries (in-process tabix)**: Genomic region/variant range queries no longer shell out to the `tabix` subprocess. `GCloudTabixBase._stream_range` parses the bgzf `.tbi` index in Python (`app/services/tabix_query.py`), turns the query regions into the minimal set of compressed byte ranges, fetches them **concurrently over the pooled aiohttp GCS session** (a `Range:` header GET per range, bounded by the process-wide fetch semaphore described under "Bounding open sockets / file descriptors"), decompresses the bgzf blocks with stdlib `zlib`, and filters to records overlapping the regions — producing the same records `tabix -R` would, in coordinate order. This replaces the old single serial `tabix` subprocess that issued ~one HTTP range request per region (the dominant latency for large variant batches): an 888-variant single-resource query dropped ~18 s → ~4–5 s and small batches ~1.5 s → ~0.3 s. See "GCS access" below for details (header retrieval still uses `tabix -H`). Indexed `.tsv.gz` files remain on GCS. Exome variant results are served for genebass (filtered to mlog10p > 4), IBD exome (resource: `ibd_exome_2026`, 3 phenotypes: IBD, UC, CD, filtered to mlog10p > 4). Data files are in `exome_results/` on GCS. Individual trait exome variant results can be queried by phenotype via the `exome_results_by_phenotype` endpoint, which uses prefix/suffix patterns to locate per-trait data files. Exome variant columns include `n_cases`/`n_controls` (nullable) and `trait_original`. Gene-based burden results use a separate column schema with `trait_original` and `flags` columns (`gene_based_header_schema` in `app/config/gene_based_results.py`), and are served both per-gene-across-traits from a combined `file` and per-trait from `prefix`+`suffix` files that are unfiltered for every dataset. Those per-trait burden files are bgzipped (unlike the historically plain-TSV per-phenotype credible-set and genebass exome files) so the same objects can also be tabix-queried for one gene; `_stream_file` therefore gunzips any `.gz`/`.bgz` object on the way out, since every caller of it wants text. When several datasets share one combined file (e.g. the external pseudo CS file bundling `covid_hgi`, `pgc_scz`, `pgc_bip`, `gp2_pd` and `ibd_gwas` under `credible_sets/ext_pseudo/`), `DataAccess.stream_range*` dedups by `all_cs_file`/`all_exome_file` so tabix runs once, and `tsv_line_iterator` is given a `resource_filter` that drops shared-file rows belonging to resources not in the request. Per-phenotype individual files live in per-source subdirs `ext_pseudo/individual/<source>/` (`covid_hgi`, `pgc_scz`, `pgc_bip`, `gp2_pd`, `iibdgc` — the source name, not always the dataset id) so that datasets sharing a resource (e.g. `pgc_scz` + `pgc_bip` → `pgc`) don't collide on phenotype lookups. Not every dataset under a shared resource shares a file, though: `pgc_scz_finemap` (the published PGC schizophrenia FINEMAP credible sets, `dataset` column `PGC_SCZ_2022`) has its own `all_cs_file` under `credible_sets/pgc_scz_finemap/2022/` with its own `individual/` prefix and `stats_file`, so it needs no shared-file resource filter — but it does sit on resource `pgc` next to the pseudo `pgc_scz` and covers the same phenotype code `SCZ`, so a request scoped to resource `pgc` returns both the fine-mapped and the pseudo credible sets for that trait. Summary-stats datasets are served from per-phenotype `prefix`+`suffix` files keyed by phenotype; `finngen_ukbb_pqtl` (resource `finngen_ukbb`, `data_type=pqtl`, v1) is a 3-way inverse-variance pQTL meta-analysis of FG2-3K (Olink 3K) + UKB-PPP (Olink 3K) + FG3 Cross-Batch (Olink HT 5K) over 2,831 proteins (max combined N=48,703, GRCh38/dbSNP b156), keyed by gene symbol with per-study and combined-meta columns. It is summary-statistics only (no credible sets/colocalization — `products` auto-derives `summary_stats` for it) and is served from the UNFILTERED (union) tier (the filtered tier is a lead-study subset, not a union).
3. **Service layer**: `app/services/` contains data access classes (inheriting from `GCloudTabixBase`) that handle tabix queries, parsing, and result formatting. Metadata harmonization uses `build_harmonizer_config(dataset_id)` from the registry to get harmonizer settings. `config_util.get_metadata_dataset_ids_for_resource(resource, include_coloc_partners=)` picks the datasets whose metadata populates a resource's `/resource_metadata` and `/trait_name_mapping`: always the product-backed datasets (credible sets, exome, gene-based), and — when `include_coloc_partners` is set — also coloc-partner datasets of the resource that ship no product of their own. The motivating case is `finngen_kanta_r12` (the R12 Kanta lab GWAS retained only as the eQTL/caQTL coloc partner): coloc results reference it by **bare OMOP ids** (e.g. `3001122`), whose names live in its `finngen_kanta_pheno_202503.json` metadata. The `/resource_metadata/{resource}` endpoint and `get_resource_metadata` (raw, feeding `/trait_name_mapping`) request partners so those names resolve, while the **search index leaves partners out** (`include_coloc_partners=False`) since they are not independently queryable. Harmonized metadata is cached per `(resource, include_data_type, include_coloc_partners)`. `GeneNameAndPositionMapping` provides gene coordinate lookups (per GENCODE version) used by `SearchIndex` and chromatin peaks streaming to enrich results with genomic positions. `GeneGroupService` (`app/services/gene_group_service.py`) reads the three HGNC gene-group CSVs with polars' `read_csv` (all columns as strings via `infer_schema_length=0`, then ids coerced explicitly) at startup and builds an in-memory map from `hgnc_id` to its FULL gene-group lineage (leaf family plus all ancestor families via the precomputed transitive closure), plus the inverse `group_id -> member hgnc_ids` for descendant resolution. The three inputs are HGNC-native comma-separated CSVs: `gene_has_family` (`hgnc_id`, `family_id` leaf links), `hierarchy_closure` (already-transitive `child_fam_id`/`parent_fam_id`/`distance` rows; only proper ancestors with `distance > 0` are kept, the leaf is unioned in from `gene_has_family`), and `family` (`id` -> `name`, also indexed lowercase for case-insensitive name lookups). File paths come from the active profile's `genes` config keys `gene_has_family_file`, `hierarchy_closure_file`, `family_file` (alongside the existing `hgnc_file`). These three keys are present in BOTH profiles — `app/config/profiles/finngen/genes.py` (under `gs://finngen-commons/results_api_data/mapping_files/`) and `app/config/profiles/daly/genes.py` (under `gs://daly-genetics-results/mapping_files/`) — pointing at `hgnc_gene_has_family.csv`, `hgnc_hierarchy_closure.csv`, and `hgnc_family.csv`, which must be uploaded to each profile's GCS `mapping_files/` directory for the feature to activate. Loading is resilient: if the paths are unconfigured, or a file is missing or unreadable (e.g. not yet uploaded to GCS), a warning is logged and the group map is left empty so startup never fails (mirroring the coordinate-loading try/except in `SearchIndex._load_genes`). Accessors: `group_ids_for_hgnc_id(hgnc_id)`, `groups_for_hgnc_id(hgnc_id)` -> `[(group_id, group_name)]`, `members_of_group(group_id=..., group_name=...)` -> set of member `hgnc_id`s (any leaf/ancestor/root group resolves to all descendant members), `resolve_group_id(group_name)`, `group_name(group_id)`, and `is_loaded()`. Wired through the service container as `gene_group_service` (`create_gene_group_service` in `app/core/service_container.py`) and exposed via `get_gene_group_service()` in `app/dependencies.py`. To turn the `hgnc_id`s returned by `members_of_group` into symbol/ensembl/coordinates, `SearchIndex._load_genes` now also stores each gene record's `hgnc_id` and builds a `genes_by_hgnc_id` lookup (accessor `get_gene_by_hgnc_id(hgnc_id)`); this is the single bridge from HGNC ids back to the symbol/ensembl/coords already loaded from the same HGNC complete-set + GENCODE source (no coordinate logic is duplicated, and chrom keeps the API-wide X=23 convention since it comes from the GENCODE coords lookup). **HGNC id format**: the gene-group files use BARE numeric ids (`3023`) while the complete set (and thus `genes_by_hgnc_id`) uses the prefixed `HGNC:3023` form, so `GeneGroupService` canonicalizes every id to the `HGNC:NNNN` form (via `_canonical_hgnc_id`) when building its maps, and `get_gene_by_hgnc_id` also tolerates the bare form on lookup. Without this, every member resolved to null symbol/coords. The `gene-groups` router (`app/routers/gene_groups.py`, registered in `app/server.py`) joins these two services: it requires exactly one of `group_id`/`group_name` (400 otherwise), resolves a name case-insensitively (404 if unknown, both for an unresolvable name and for an unknown id), and returns `{group_id, group_name, exclude_olfactory, count, members:[{hgnc_id, symbol, ensembl_id, chr, gene_start, gene_end}]}` sorted by symbol (null symbols last). Members lacking a search/coords record are still listed with null fields rather than dropped, and if `is_loaded()` is False (group files not yet uploaded) it logs and returns an empty member list (count 0) instead of erroring. Olfactory receptors are GPCRs that dominate large families (e.g. the G protein-coupled receptor group) by sheer count; the optional `exclude_olfactory` query param (default False on the raw endpoint; the mcp-server tool defaults it to True) drops any member whose lineage contains the `Olfactory receptors` group via `members_of_group(..., exclude_olfactory=True)`. The same router also exposes `GET /gene/normalize?symbols=<comma-separated>`, which resolves each input gene symbol/alias/previous symbol to its current approved HGNC symbol and returns `{mappings:[{input, approved, matched_on}], unresolved:[...]}`. It reuses `SearchIndex.normalize_symbol`, which performs an EXACT case-insensitive dict lookup (built once, lazily, from `self.genes`' approved `symbol` plus merged `aliases`/previous symbols — the free-text gene `name` and ensembl id are deliberately excluded) rather than the fuzzy `search()` path, so normalization never yields ranked near-miss false positives. `matched_on` is `approved` when the input is already an approved symbol, else `alias_or_previous` (the HGNC load merges alias and previous symbols without retaining which list a match came from).
4. **Gene-indexed QTL credible sets**: `/credible_sets_by_qtl_gene/{gene}` reads a dataset's `all_cs_qtl_file` — the same credible set rows as `all_cs_file` plus the molecular trait's gene coordinates in `trait_chr`/`trait_start`/`trait_end`, tabix-indexed on those columns (`-s20 -b21 -e21`). Rows are fetched at the queried gene's start position and then filtered by an **exact string match** on `trait_start`+`trait_end` (`tsv_line_iterator_qtl` in `app/core/streams.py`), so the file's coordinates must come from the same GENCODE version as the dataset's `gencode_version` — coordinates from any other version silently match nothing. `stream_qtl_gene` builds the merged cross-resource header from the first matching file, so every `*.qtl.tsv.gz` must carry the identical 22-column schema (no dataset-specific extra columns). **`finngen_caqtl` is the one dataset whose trait is not a gene**: the trait is a chromatin peak, so its qtl file is built by joining credible set rows to the Open4Gene peak-to-gene table on (peak, cell type) — cell-type-matched, so a signal is only attributed to a gene in the cell type where the link was significant — and emitting one row per linked gene. There, `trait` holds the linked gene symbol while `trait_original` and `cs_id` keep the peak id (in every other QTL dataset `trait` is identical in both files). This is what makes "which caQTL signals are linked to this gene, per cell type" answerable at all: the chromatin-peaks table (`peak_to_genes`) is tabix-indexed on peak coordinates and has no gene-keyed inverse. The file is produced by `scripts/create_caqtl_gene_indexed_qtl_file.{py,sh}` in the genetics-results-munge repo; 82,202 of the 152,321 caQTL peaks that have credible sets carry a gene link, expanding to roughly 10–15 M rows.
5. **Gene-indexed peak-to-gene table**: the Open4Gene table is tabix-indexed on PEAK coordinates, which answers `peak_to_genes` but leaves a gene's peaks scattered across the file. `/gene_to_peaks/{gene}` therefore reads a second copy (`file_by_gene` in the profile's `chromatin_peaks` config) holding the same rows plus three trailing columns with the linked gene's locus, sorted and indexed on those (`-s21 -b22 -e23`), then by peak position so each gene's block stays in the order the cross-resource merge expects. Because a locus query returns every row whose gene overlaps the queried one, rows are filtered by **ENSG** (`tsv_line_iterator_chromatin_peaks_by_gene`) rather than by coordinate equality — unlike the qtl path above, this keeps the endpoint working when the file's GENCODE version differs from the request's, and the query is issued for every version the gene is known in so the file's own version is always covered (`_stream_range` merges overlapping byte ranges, so extra regions cannot duplicate rows). The trailing locus columns are dropped on read and gene coordinates are re-derived from the requested `gencode_version`, so `gene_to_peaks` and `peak_to_genes` return byte-identical rows for a peak they share (asserted in `tests/test_chromatin_peaks.py`). A resource without `file_by_gene` is skipped; if no requested resource has one the endpoint 404s. Built by `scripts/create_gene_indexed_peak_gene_file.{py,sh}` in the genetics-results-munge repo (1,070,025 rows, all 12,445 genes mapped in v32).
6. **Routing layer**: `app/routers/` defines endpoints that validate input, call services, and return formatted responses

### Authentication

- Auth dependency applied globally via `dependencies=[Depends(auth_required)]`, with the `@is_public` decorator exempting individual endpoints
- Enforced only when `REQUIRE_AUTH` is truthy (default false, so local runs are open); the deployed service sits behind IAP/oauth2-proxy
- Credentials accepted by `app/core/auth.py`, in order: an `Authorization: Bearer` token matching the shared `INTERNAL_API_SECRET` (service-to-service); a dotted token treated as a Google Identity Token verified with `google-auth` (**deprecated**; per-user API tokens are the recommended programmatic credential); a non-dotted token validated as a user API token against `CHAT_BACKEND_URL` `/v1/tokens/validate`. Falling back to the `X-Goog-Authenticated-User-Email` header set by IAP/oauth2-proxy (browser sessions). Decision record: `genetics-results-suite/docs/project-spec.md`, "Programmatic credentials: why the per-user API key, not the Google id_token"
- **The identity header is only honoured behind a trusted-proxy marker.** Anything with network reach to port 4000 can set `X-Goog-Authenticated-User-Email` to any string, so `get_authenticated_user()` believes it only when the request also presents `Authorization: Bearer $INTERNAL_API_SECRET` (`is_internal_caller()`) — the marker the in-cluster proxies hold and an unprivileged pod does not. It then applies the same `ALLOWED_EMAILS`/`ALLOWED_EMAIL_DOMAINS` allow-list as the Google-JWT path. Either check failing yields `None` (fail closed → 401 from `auth_required`, `authenticated: false` from `/api/v1/auth`) rather than a 403, so the public status endpoint keeps its contract. `middleware_usage_logging._extract_user_from_header` applies the identical rule — marker **and** allow-list — before attributing an `endpoint_access` record, so a forged header cannot name someone else in the logs and an address the auth path refuses is not logged as the requester either
- **Precedence in `get_verified_user()`**: the asserted identity is resolved *before* the bearer is mapped to a service identity, because checking the bearer first would collapse every browser request to the generic `mcp-tool` and lose the real user for authorization, for `request.state.authenticated_user` and for the usage log. In order: (1) marker + allow-listed identity header → **that email**; (2) marker + identity header that is *not* allow-listed → **`None` → 401**, deliberately not downgraded to `mcp-tool`, since a downgrade would let anything holding the shared secret launder a refused identity into a working request; (3) marker alone → **`mcp-tool`** (unchanged); (4) user API token / Google Identity Token (the latter deprecated) → that identity (unchanged); (5) identity header alone → **`None` → 401**, the vulnerability this closes. The resolved address is returned **trimmed and lower-cased** (matching is case-insensitive and whitespace-tolerant, so returning the raw spelling would split one person across several identities in `endpoint_access`); `middleware_usage_logging._extract_user_from_header` normalizes identically. A *literally* empty header value is no assertion and falls to (3), but nginx never sends one — `proxy_set_header` drops a header whose value is the empty string, so an empty oauth2-proxy `$email` puts the bare prefix `accounts.google.com:` on the wire instead. That is truthy, so it is case (2): it asserts the empty address, which no allow-list admits → **401**. Unreachable in production (oauth2-proxy cannot return 200 for `/oauth2/auth` without an email — its own domain check needs one), but it is a rejection, not a downgrade
- **Allow-list matching** (`_email_allowed`) is case-insensitive on both the asserted address and the configured entries, because oauth2-proxy lower-cases before its own domain check and would otherwise admit a mixed-case address this service rejects. A literal `*` in `ALLOWED_EMAIL_DOMAINS` means "any domain", matching oauth2-proxy's reading of the same value; without it, a deployment set to `*` would authenticate everyone at the proxy and reject everyone here. `is_internal_caller` compares the token as **bytes** — `hmac.compare_digest` on `str` raises `TypeError` for non-ASCII, and it runs inside ASGI middleware before routing, so a non-ASCII bearer would surface as a 500 instead of failing closed
- **Deployment ordering across repos**: the marker only works if the caller sends it, and genetics-results-browser's `bff/passthrough.ts` is what attaches it to browser traffic. **bff must be rolled out before results-api** — a results-api carrying this rule in front of a bff that does not yet send the bearer 401s every non-variants browser request. The reverse transitional state (bff new, results-api old) is safe indefinitely: the old API accepts the bearer as an internal call. Full state table in the suite repo's `docs/project-spec.md`, "Ordered rollout: the trusted-proxy marker"
- Google Identity Tokens (**deprecated**; per-user API tokens are the recommended programmatic credential, and this branch is not being switched off without notice) must carry an `aud` in `GOOGLE_TOKEN_AUDIENCE` and a verified email in `ALLOWED_EMAILS` or a domain in `ALLOWED_EMAIL_DOMAINS`. `id_token.verify_oauth2_token` skips audience verification when no audience is passed, so with `GOOGLE_TOKEN_AUDIENCE` unset any Google-signed token of an allow-listed email is accepted — including one minted for a different OAuth client; that case logs a warning. Set, the check is worth **cross-OAuth-client** replay protection only: the deployed value is the gcloud CLI's public client id, so a token the same user handed to another service documenting the same `gcloud auth print-identity-token` flow carries the identical `aud` and still passes — the email allow-list is the access control
- Public (`@is_public`): health check (`/healthz`), root (`/api/v1`), `/api/v1/auth`, `/rsid/variants` (GET/POST), and the variant-set endpoints
- **The `@is_public` decorator no longer means "anonymous" by default (`ANONYMOUS_SURFACE_MINIMAL`).** `app/dependencies.is_public_endpoint` serves a route with no principal resolved only if it is in `ALWAYS_ANONYMOUS_PATHS` — `/healthz` alone, for the kubelet, which holds no credential and whose probes are exempt from NetworkPolicy — whenever `ANONYMOUS_SURFACE_MINIMAL` is on. **It defaults to on**, and `SANDBOX_ENABLED=true` forces it on regardless, so disabling the sandbox during an incident cannot re-widen the surface (`genetics-results-suite-rhh`; the earlier version keyed the surface directly on `SANDBOX_ENABLED`, which failed *open* on the action taken under pressure). Widening it is an explicit `ANONYMOUS_SURFACE_MINIMAL=false`, refused while the sandbox is enabled. The parse is inverted relative to every other boolean in `app/config/common.py` — unset is on, only an explicit falsey spelling (`0/false/no/off/disabled/n/f`, whitespace- and case-insensitive) turns it off, and an unrecognised value keeps the surface minimal *and logs a warning naming the value*. Why: the anonymous surface is what lets a sandbox script shed the per-execution counters in `app/core/sandbox_budget.py`, which are admitted from the `Authorization` header. Pinned by `tests/test_anonymous_surface.py`, which reads the live route table (so a new `@is_public` decorator cannot reopen it silently) and pins the shipped default as the running process reads it
- **Deployment ordering, three services: bff → mcp-server → results-api.** Turning the minimal surface on by default changes behaviour at the *next results-api deploy*, and two callers currently present no credential on the six affected routes (`/api/v1`, `/api/v1/auth`, `/api/v1/variant_sets`, `/api/v1/variant_sets/{name}`, `/rsid/variants` GET+POST). (1) **The browser**: genetics-results-browser's BFF attaches `INTERNAL_API_SECRET` only on its *typed* upstream routes (`bff/upstream.ts`); these six are served by its *generic passthrough* (`bff/passthrough.ts`), which attaches nothing — measured through the **deployed** BFF with no headers, `/api/v1/auth` answers 200. The passthrough fix is **un-deployed** (it exists only in that repo's `db-only-architecture` worktree), so a results-api deploy ahead of it 401s the browser's login-state probe, its variant sets and its rsid lookups. (2) **An mcp-server pod with `INTERNAL_API_SECRET` unset** — its `secretKeyRef` is `optional: true`, so it starts credential-less; `genetics-results-suite-618` made that a startup failure in genetics-mcp-server. Deploying 618 first does not keep such a pod working: it turns a bare, unexplained 401 on every tool call into a CrashLoopBackOff naming the variable — diagnosability, not availability. **Nothing enforces the order.** The suite repo's `scripts/rollout.sh` documents it in its `ORDERING:` header; `scripts/deploy.sh` restarts every Deployment in one loop with no waiting and with results-api *before* chat-backend and mcp-server
- **`GET /api/v1/auth` is not an identity oracle.** Being public, it answers a caller holding no credential, which is the shape that made chat-backend's `GET /chat/v1/auth` an unauthenticated admin-membership oracle (`genetics-results-suite-th2`). Measured against the running app for `genetics-results-suite-r0l`: no headers → `authenticated: false`; **forged identity header alone → `authenticated: false`, the address is not echoed back**; marker + allow-listed identity → that address, normalized; marker alone → `authenticated: false`, because the handler asks `get_authenticated_user`, which reports only the proxied *person*, never the service. `tests/test_auth_endpoint_identity.py` pins all four and runs offline
- The docs UIs and OpenAPI schema are registered explicitly (`/api/v1/docs`, `/api/v1/redoc`, `/api/v1/openapi.json`) rather than via FastAPI's `docs_url`/`openapi_url`: Starlette's `add_route` does not apply the app-level `dependencies`, so the built-in routes served the full schema unauthenticated

### Sandbox limits

Design of record: `genetics-results-suite/docs/code-execution-security.md` §4. Every limit here
applies **only** to a request carrying a sandbox execution token; a verified non-sandbox
principal, an `@is_public` route and a `REQUIRE_AUTH=false` dev run are untouched, never buffered
and never accounted (`app/core/limits.py` states the rule and why it is broader than db-api's).

- **Per response: 16 MiB** (`SANDBOX_MAX_RESPONSE_BYTES`), enforced by `SandboxResponseCapMiddleware` in `app/middleware.py`, registered innermost of GZip so it measures the payload the caller decodes. A capped response is buffered — bounded by the cap itself — so the answer can be a **429 rather than a truncated stream**; over the cap the middleware raises out of `send`, which abandons `StreamingResponse`'s generator instead of letting it run to completion with its chunks discarded. There is deliberately **no row cap**: counting rows meant `json.loads` over the whole body on the event loop, a memory amplifier only a sandbox caller could trigger, and it never bound TSV — the default `format` of every bulk range endpoint
- **Per execution (`jti`), in `app/core/sandbox_budget.py`** — the analogue of db-api's `_jti_bytes`, deliberately the same shape: one in-process map keyed on `jti`, checked **before** the handler runs, 429 rather than truncation. All four are env-configurable and default to: aggregate response bytes **1 GiB** (`SANDBOX_AGGREGATE_RESPONSE_BYTES_BUDGET`), requests **1000** (`SANDBOX_MAX_REQUESTS_PER_EXECUTION`), concurrent requests **4** (`SANDBOX_MAX_CONCURRENT_REQUESTS`) and **8** pod-wide across all executions (`SANDBOX_MAX_CONCURRENT_REQUESTS_TOTAL`). Concurrency is the one with a *memory* failure mode rather than a cost one — each in-flight capped request buffers up to 16 MiB on a `replicas: 1` pod that preloads the gene maps and the search index
- **Where they live and why.** Admission and release sit inside `SandboxResponseCapMiddleware`, whose `finally` the ASGI contract puts after the last byte of the response, a `StreamingResponse` included. The reason a FastAPI dependency teardown is the wrong place is *not* that a streaming generator outlives it — measured on FastAPI 0.136.1, a `yield` dependency's exit code runs **after** the response body, so for a matched route the two placements are indistinguishable — but that `admit` runs for **every** request while a dependency is solved only for a **matched route**: an unmatched path 404s out of the router with no dependency entered, stranding the concurrency slot permanently (and `_sweep_locked` will not evict an entry with `in_flight > 0`). `test_an_unmatched_route_releases_its_slot` is the test that kills that mutation. The middleware verifies the bearer itself (`_sandbox_principal`, non-raising) because `request.state.sandbox_principal` is only set later by `auth_required`, and a request-count bound has to be admitted before the handler runs. Same `is_sandbox_shaped` routing and same HS256 decode, so it cannot disagree with what `limits.caps_for_scope` reads off the request state; an invalid sandbox-shaped bearer is left to `auth_required`'s 401
- **Bytes are charged as *sent*,** taken from the cap middleware's own buffer, so the two agree by construction. **Every status is buffered, capped and charged, not only 2xx** — "an error body is small" was false, since FastAPI's 422 handler echoes the offending input (measured: a 100 000-char query param produced a 100 144-byte body; a 200 014-byte body was delivered under a 500-byte cap with `bytes_sent` left at 0), which made the real egress bound the request count × whatever fits in a URI or a request body. The status only changes the *rejection*: an over-cap 2xx becomes a 429, an over-cap non-2xx keeps its own status with the same bounded stub body (rewriting a 404 into a 429 loses the answer, `tests/test_response_caps.py`). Only that stub case is uncharged — its bytes never went on the wire — and it still consumes a request slot
- **Reject, never queue.** Queueing would hold the request while the sandbox's ~120 s wall clock keeps running, which the script cannot distinguish from slow data, and can admit work that completes after its execution is already dead. Every 429 carries `code`, `limit` and `observed`: `sandbox_response_bytes`, `sandbox_aggregate_bytes`, `sandbox_request_count`, `sandbox_concurrency`, `sandbox_concurrency_pod`, `sandbox_execution_tracker_full`
- **Cleanup cannot evict a live execution** — the one deliberate departure from db-api, whose 1024-entry LRU *can* drop a running counter and silently reset its budget, the fail-open direction. An entry is evictable only once its token is past the point `verify_sandbox_token` would still accept it (`exp` + the verifier's leeway, so no further request can present that `jti`) **and** nothing is in flight under it (covering a stream that outlives its own token). The map is hard-bounded at `SANDBOX_MAX_TRACKED_EXECUTIONS` (4096, swept lazily when a new `jti` arrives); at the bound the **new** execution is refused, never a running one evicted. Entries live at most one token lifetime (~305 s)
- **In-process, so `replicas: 1` is load-bearing** — N replicas give one execution N × every limit above. `k8s/deployments/results-api.yaml` in the suite repo carries a comment on `replicas: 1` saying so, matching db-api's
- **What these limits do *not* bind.** (a) They only bind a request that **volunteers a token**: `_sandbox_principal` reads the `Authorization` header, and with no header `admit` is never called, so the request is counted against nothing. results-api used to answer 200 with no credential on its seven `@is_public` routes while the sandbox's NetworkPolicy reaches `results-api:4000` directly, bypassing auth-gateway (measured: 20/20 header-less requests served with the counter map empty). `app/core/limits.py`'s "omitting the header cannot buy a looser limit" invariant therefore holds for the per-response byte cap **only**. The **no-credential** half is closed in `app/dependencies.py:is_public_endpoint` (`genetics-results-suite-0lf`): with `ANONYMOUS_SURFACE_MINIMAL` on — its default since `genetics-results-suite-rhh`, and forced by `SANDBOX_ENABLED` so disabling the sandbox cannot re-open it — `/healthz` is the only route servable with no principal. The **internal-secret** half is still open: that secret satisfies `is_internal_caller` while `_sandbox_principal` accepts an HS256 sandbox token only, so such a caller is served with `admit` never called; it closes in `genetics-results-suite-4h6.7` + `4h6.14`, and `tests/test_anonymous_surface.py` pins both halves. (b) `sandbox_execution_tracker_full` and the pod-wide concurrency limit are pod-wide, hence **cross-tenant denial surfaces** — sized far above honest use rather than made fair
- **All five env vars are declared in `k8s/deployments/results-api.yaml`** (suite repo) at their defaults, so they are tunable without a rebuild, and each is validated at import: a value below 1 turns a `>=` ceiling into "reject every sandbox request", and `..._TOTAL` below the per-execution value makes the per-execution number a lie — both raise rather than fail silently at the first request
- Tests: `tests/test_response_caps.py` (per-response cap, 18 tests) and `tests/test_sandbox_budget.py` (per-execution limits, 30 tests), both in the `offline` lane. Production impact is nil today — no sandbox Deployment exists and `SANDBOX_ENABLED` is `"false"` — so these tests are the only thing that will report a regression

### Testing

- Most tests in `tests/` are integration tests: they take the `server_url` fixture and make real HTTP calls with `requests`
- **`server_url` boots the app in-process when no `--server-url` is given.** The session fixture picks a free ephemeral port, runs the real `app.server:app` under uvicorn in a daemon thread (`loop="asyncio"`, matching `run_server.py`), waits for `Server.started`, and yields `http://127.0.0.1:<port>`. Startup runs the full `lifespan` — tabix header warming, gene maps, search index, gene-disease load, and the cross-resource smoke query — so it needs working Google credentials and GCS access, and takes ~25 s once per session. Passing `--server-url` skips all of this and tests the given deployment exactly as before. This existed because the previous default was a bare `http://localhost:4000`: with nothing listening the whole suite failed, and with the *wrong* service listening (the Genetics Chat API also defaults to 4000) it "ran" against a stranger — either way the assertions inside those tests pinned nothing (`genetics-results-suite-w09`)
- **Two lanes, assigned automatically** (`pytest_collection_modifyitems` in `tests/conftest.py`, markers registered in `pyproject.toml`):
  - `integration` — every test taking `server_url`, plus a handful marked explicitly because they need the network for another reason
  - `offline` — everything else. Classification is by fixture, not by memory, so a newly added test defaults to `offline` and runs in the credential-free lane rather than joining a pile that silently never executes
  - `pytest` runs both (booting the app); `pytest -m offline` runs the no-network subset; `pytest -m integration` runs only the live ones
  - **The classification is fail-open for new GCS-touching tests.** It keys on the `server_url` fixture, which is the only signal available at collection time — so a new test that takes no fixture but constructs `DatasetMapping()` (or otherwise reaches GCS) is filed as `offline` and breaks the credential-free run for everyone. It breaks loudly, not silently-green, but the fix is to mark such a test `@pytest.mark.integration` by hand, not to expect the auto-classifier to notice
  - The same fail-open applies one level up, at **import** time: collection imports every test module whatever the mark expression, so an `app` module that reaches the network while being imported takes the whole offline lane down with it. That is what `app/core/streams.py` used to do — it built a `DatasetMapping()` at module scope — which cost four modules and six tests their place in the lane and required a `_NEEDS_GCS_AT_IMPORT` exclusion list in `tests/conftest.py`. It is now built lazily by `get_dataset_mapping()` (bound once per stream by each `tsv_line_iterator_*`, so the per-row cost is unchanged) and the exclusion list and its report header are gone. **`DatasetMapping` was not the only import-time credential dependency**, and the trap is wider than GCS: `app/core/streams.py` also calls `setup_logging()` at module scope, and with the default `DEPLOY_ENV=dev1` that takes the `use_cloud_logging_api` branch and constructs a `google.cloud.logging.Client()`, which resolves Application Default Credentials and a project. Credential-free that raised at import, so collection ended in 1 error and `-m offline` ran **zero** tests — and only one module showed it, because `_logging_initialized` was set before the risky call, so every later importer skipped setup and imported fine. `setup_logging()` now catches that failure (`google.auth.exceptions.GoogleAuthError` — google-cloud-core raises a bare `OSError` for the missing project — clears the half-installed handlers, falls back to `_setup_stdout_logging()` and warns once so a real production auth failure is visible), and `_logging_initialized` is set only after setup completes. With credentials present the cloud handler is still installed and nothing changes. Measuring this needs a *genuinely* credential-free environment: on a GCE VM the instance metadata server is itself an ADC source, so unsetting `GOOGLE_APPLICATION_CREDENTIALS` and emptying `CLOUDSDK_CONFIG` is not enough — `HOME` must be empty and `GCE_METADATA_HOST`/`GCE_METADATA_IP` pointed at a dead address as well. So measured: `pytest --collect-only -q` → 564 collected, no error; `-m offline` → 182 collected / 382 deselected; `pytest -m offline` → 182 passed, 382 deselected (`genetics-results-suite-917`)
- **Exactly one test is `@pytest.mark.integration` by hand**: `test_sandbox_token_auth.py::test_alg_none_is_not_accepted`, because verifying an `alg: none` token makes PyJWT fetch Google's OAuth signing certificates over the network. Every other test's lane comes from whether it takes `server_url`
- **The HLA response formats are pinned against each other.** Only the JSON path types its rows through `app/routers/hla.py`'s `_HLA_HEADER_SCHEMA` (and 500s when the data no longer matches it); the TSV path streams the underlying columns through `TimedStreamingResponse` untouched and never consults the schema. So a rename that reaches one and not the other used to be caught by nothing — the download-header failure mode of `genetics-results-suite-5wm`. `tests/test_hla.py::TestHlaAssociations::test_tsv_header_matches_the_header_schema` asserts the served TSV header equals `list(_HLA_HEADER_SCHEMA)`, in order and in full; both mutations (renaming a schema key, deleting one) fail it. The TSV path is deliberately left non-validating: it is a byte pass-through, and making it reject unknown columns would turn an additive data change into a 500 on the download route (`genetics-results-suite-7yg`)
- Self-contained unit tests also live in `tests/` (e.g. `test_gene_group_service.py`, which writes small CSV fixtures and exercises `GeneGroupService` directly, and `test_auth_header_trust.py`, which builds Starlette `Request` objects and asserts the identity-header trust rule); these need neither a live server nor GCS access

### Deployment

- Docker container built with htslib (for tabix) and gcloud SDK
- GCS authentication via Workload Identity or service account key. `GCloudTabixBase.ensure_gcs_token()` fetches/refreshes the OAuth token used by the remaining tabix subprocesses (`tabix -H` headers, gnomad) — exported as `GCS_OAUTH_TOKEN`; the whole check-and-refresh (including first init) holds `_gcs_token_lock` so concurrent first calls can't race on the env var. Range reads instead authenticate via the pooled aiohttp/`gcloud-aio` session (`storage._headers()`). htslib reports transient GCS access failures (timed-out/partial HTTPS requests) as misleading `Invalid argument` / `No such file or directory` / index-load errors and never retries them, so `_get_header` retries `tabix -H` up to `_TABIX_MAX_ATTEMPTS` (3) times with exponential backoff; the in-process range fetchers (`_fetch_full` for the `.tbi`, `_fetch_blocks` for data) retry the same way on transient errors. The aiohttp GCS client + `gcloud-aio` `Storage` are created lazily via `_ensure_storage()` on first use (now also used by the range path) and recreated if a prior session was closed. Header retrieval has both a blocking (`_get_header`, `subprocess.run`) and a non-blocking async (`_get_header_async`/`_cache_header_async`, `asyncio.create_subprocess_exec`) form; the data-access objects no longer fetch headers eagerly in `__init__` (which blocked the event loop on a `tabix -H` per file) — instead the header is fetched lazily by `get_header()` and prefetched (non-blocking) at startup by each object's `warm()` (`tabix -H` also downloads the `.tbi` index, warming that cache too).
- **In-process tabix range reads** (`app/services/tabix_query.py` + `GCloudTabixBase._stream_range`): the dominant cost of large variant batches was htslib issuing one HTTP byte-range request per region **serially** over a single connection (~20 ms/region in-region — the same query on a local file copy is ~36× faster, and the API VM is co-located with the bucket, so it is round-trip latency, not bandwidth or WAN). The replacement: (1) the bgzf-compressed `.tbi` index is fetched once via the pooled session and parsed into bin/linear/chunk structures (cached in-process per file; the raw `.tbi` is also persisted to the existing `/tmp/tbi_cache`); (2) query regions map (via `reg2bins` + linear-index min-offset) to compressed chunk byte ranges, merged so each boundary block is read once; (3) `_fetch_blocks` streams each range over its instance's aiohttp session with a `Range:` header and stops after the final needed bgzf block (avoiding a fixed 64 KiB over-read per range); (4) decompress (`zlib`, gzip/bgzf member-by-member) + record filtering run in a **`ProcessPoolExecutor`** (`_get_filter_pool`, `min(4, cpu-1)` workers, override `TABIX_FILTER_WORKERS`) split into contiguous sub-batches, because the per-line parsing is GIL-bound and would otherwise pin one core while the others idle — this is what makes the all-resources batch parallelize.
  - **Bounding open sockets / file descriptors**: each data-access object owns its own aiohttp session+connector (gcloud-aio's `Storage`/`Token` binds a token session per instance, so a *shared* connector breaks token refresh with "Event loop is closed"). To stop a fan-out from opening thousands of sockets at once — which exhausted the process FD limit ("Too many open files"), since an all-resources request touches ~12-15 files — every range fetch acquires a **process-wide `asyncio.Semaphore`** (`_get_fetch_semaphore()`, size `_GCS_MAX_CONNECTIONS`=128, override `GCS_MAX_CONNECTIONS`). This caps *total* concurrent fetches (hence sockets) across all files **and overlapping requests**, so socket count stays bounded regardless of request concurrency (measured peak ~370 for two concurrent 888-variant all-resources requests vs ~730 for a single request before the cap). Connector `keepalive_timeout` is 5 s so idle sockets from a burst free quickly. This is purely a per-request concurrency spike, not an FD leak — idle FD count returns to baseline. The container entrypoint (`start.sh`) also raises `ulimit -n` to 65536 as defense-in-depth, and the k8s deployment sets `TABIX_FILTER_WORKERS`/`GCS_MAX_CONNECTIONS`. The filter has a fast path for point queries on point records (byte-level `(seqname, pos)` set membership, no int parsing) and a general interval-overlap path; output is the matching record lines in coordinate order, identical to `tabix -R` (verified against `tabix` and the integration suite). Net measured: 888-variant all-resources ~30 s → ~12 s, single-resource ~18 s → ~4–5 s, small batches ~1.5 s → ~0.3 s. Services that use `_stream_range` must let `GCloudTabixBase._init_storage` create the session (do not override it to a no-op as the gnomad path, which uses only its own tabix subprocess, still does).
- Default port: 4000
- Entry point: `/opt/genetics-results-api/start.sh` which initializes gcloud auth and starts uvicorn
- **Single-process startup (no reload by default)**: `run_server.py` runs uvicorn with `reload=False` unless `RELOAD` is truthy (`1`/`true`/`yes`). `run_server.py`'s `__main__` does only fail-fast file verification (`verify_all_data_files()`) before handing off to uvicorn — it deliberately does NOT construct or warm any service singletons, so all warming and the end-to-end smoke query happen exactly once, in the `lifespan` of whichever process actually serves. This keeps the two reload modes equivalent: with reload on (local dev), the warming runs in the worker subprocess that owns the serving container; with reload off (production default), it runs in the same process. Earlier versions ran a battery of `_validate_*` smoke queries in `__main__` on a throwaway event loop and then tore their warmed aiohttp sessions down via `_cleanup_services` so `lifespan` could re-warm — duplicated, discarded work that has been removed. Local dev opts into reload with `RELOAD=1`.
- **Startup data-file verification**: before uvicorn starts, `run_server.py` calls `app/services/startup_checks.py::verify_all_data_files()`, which fails startup if any configured data file is missing/unreadable. It runs concurrently (thread pool) and collects ALL failures before raising one error: (1) `tabix -H` on every fixed/combined tabix file enumerated from config — cs `all_cs_file`/`all_cs_qtl_file`, exome `all_exome_file`, gene-based `file`, coloc `credset_file`/`coloc_file`, fixed sumstats `file`, expression, chromatin peaks, open-chromatin, variant-effect, MPRA, variant-annotation, gnomad, rsid (paths shared across datasets are deduped; this also proves the tabix index loads), and (2) fsspec existence checks for non-tabix mapping files (genes `model_file`/`gene_name_mapping_file`/`hgnc_file`/per-version gencode position files, gene-disease files, and the curated `variant_set_files`). Per-phenotype `prefix`+`suffix` files are not enumerable, so they are not checked here (this includes IBD exome, which has only per-phenotype files and no combined file). Intentionally excluded: the gene-group CSVs (loaded resiliently by design) and the per-request `phenotype_markdown_template`. The open-chromatin, variant-effect and MPRA product files ARE enumerated (they were previously left to the `lifespan` warming below, which only logs and skips per-file failures, so a missing product file could not fail startup). Their config granularity differs: `open_chromatin_data` has one entry per resource so its label keys on `resource`, whereas `variant_effect_data` and `mpra_data` have one entry per **dataset** and key on `dataset_id` — necessary because the `marderstein` resource ships two distinct variant-effect predictor files (`marderstein_chrombpnet`, `marderstein_flare`) under one resource name. With both product families included, the daly profile enumerates 66 tabix files and 14 mapping files. `run_server.py` calls `setup_logging()` **before** the verification: it used to run after, so the check's own `logger.info` lines ("Verifying N tabix files…", "All configured data files verified") went to a root logger with no handlers and were discarded — the gate worked but reported nothing on success. `setup_logging()` only reads config constants and is guarded by an idempotence flag, so nothing depends on it running later.
- **Startup cache warming**: the FastAPI `lifespan` (which runs inside the uvicorn serving process) warms everything concurrently via a single `asyncio.gather`, so total startup time is the slowest branch rather than their sum. The branches: (1) `gene_disease_data` in its own worker thread (`asyncio.to_thread`); (2) a second worker thread that chains `gene_name_mapping` (the GENCODE/HGNC gene name→coordinate maps every `*_by_gene` endpoint needs) → `search_index`, which depends on it; (3) `warm_all()` on the credible-set (`DataAccess`), coloc (`DataAccessColoc`), expression (`DataAccessExpression`), chromatin-peaks (`DataAccessChromatinPeaks`), open-chromatin (`DataAccessOpenChromatin`), variant-effect (`DataAccessVariantEffect`) and MPRA (`DataAccessMpra`) services, which construct every gcloud tabix data-access object and call its `warm()` to prefetch headers and the `.tbi` index cache (non-blocking). Running the gene-disease load and the gene-maps→search-index chain as separate threads (rather than one sequential `_preload_sync`) lets the independent gene-disease read overlap the chain instead of adding to it. This is safe because `ServiceContainer.get` is thread-safe via per-name locks: independent singletons construct in parallel, and a shared dependency (e.g. `data_access`, needed by both `search_index` and the `warm_all` branches) is constructed exactly once while the other caller waits on that name's lock. Internally `GeneNameAndPositionMapping` reads the HGNC complete set once (was re-read once per GENCODE version) and builds its per-version position joins concurrently, and `SearchIndex._load_phenotypes` fetches each resource's harmonized metadata concurrently — both previously serial chains of GCS reads. Together these mean no request — variant-, region-, OR gene-keyed — pays a blocking GCS read on first use. (Sumstats serves per-phenotype files that aren't enumerable, so it isn't warmed — same reason `verify_all_data_files()` skips them.) Per-tabix-file failures are logged and skipped (`verify_all_data_files()` remains the authoritative reachability gate); a failure loading a sync singleton aborts startup loudly, as intended. After warming completes, `lifespan` runs a single end-to-end smoke query (`_smoke_query_range` in `app/server.py`): a fixed cross-resource `stream_range` over chr23:1M–2M for the `cs` data type across every resource except genebass. Unlike `warm_all` (which only opens headers/`.tbi`), this exercises the heterogeneous-file merge and schema-alignment path on the real serving loop, and raises to abort startup if that path is broken. Because nothing is warmed in `__main__` anymore, this `lifespan` warming + smoke query is the sole warming pass in both reload modes.
- **Parallel fan-out**: every cross-resource range merge (credible sets, coloc, expression, chromatin peaks, and per-phenotype sumstats) primes each file's first tabix read concurrently via `start_iterators()` (`app/core/streams.py`) before handing the iterators to `merge()`; the credible-set `DataAccess.stream_range` additionally opens its per-file access objects/streams concurrently with `asyncio.gather`. This is necessary because asyncstdlib's `merge()` seeds its heap by awaiting the first element of each iterable one-by-one, which would otherwise serialize the network-bound per-file first reads (the dominant fan-out latency). Empty iterators are dropped as before, and an iterator whose first read fails re-raises lazily when consumed, preserving the original error semantics.
